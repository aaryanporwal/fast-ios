# `simctl install` timings (15 Nov 2026)

Why the bench's "warm, changed build" row (1.5 s) is close to "warm, same
build" (1.4 s).

Set-up: Apple M5, 24 GB, macOS 27.0.1, Xcode 27.2; one new iPhone 18 Pro
simulator, iOS 27.0, stock, in a private device set; an Expo development
build of 220 MB (238 files; `MyApp.debug.dylib` 114 MB, `React.framework`
68 MB). Each line is `xcrun simctl install <udid> <bundle>` alone, timed
with a monotonic clock. Memory pressure was normal.

| Bundle installed | Round 1 | Round 2 | Round 3 |
|---|---|---|---|
| First install, right after `bootstatus -b` | 23.03 s | | |
| The same bundle again, unchanged | 2.41 s | 2.83 s | 1.79 s |
| A fresh `cp -R` copy (same bytes, new paths and dates) | 2.37 s | 2.47 s | 2.46 s |
| A copy with one extra file (what the bench does) | 1.44 s | 1.56 s | 1.58 s |
| A copy whose 114 MB main dylib has 4 KB more (a changed binary) | 1.85 s | 1.37 s | 1.71 s |

After every changed-dylib install, the installed dylib in the app
container had the new size (119,465,248 bytes), so the change was copied:
`simctl install` does not skip unchanged bundles and is not incremental in
any way these timings show. A whole reinstall costs 1.4 to 2.8 s on a
simulator that has been up a while.

Guess, not proven: the copy is cheap because it is an APFS clone on the
same volume. The slow first install comes from the simulator still starting
services just after boot.

The "about 6 s" install expected earlier was the first install on a
just-booted slim simulator (5.9 s and 4.1 s in `fast-ios run` cold runs),
not a reinstall.
